# Лабораторная работа №4

Найдите гарантию корректности при конкурентном выполнении операций.

## Цель работы

Исследуйте поведение атомарной операции `create_order` при одновременных покупках, реализуйте два разных способа защиты от гонки и добавьте защиту данных на уровне схемы БД. Механизмы и их реализацию выберите самостоятельно.

Для работы понадобятся знания транзакций, SQLAlchemy и миграций Alembic. Предполагается, что вы уже умеете создавать заказ атомарно и работать с миграциями.

## Исходные материалы и ограничения

Используйте стартовый проект, в котором `create_order` списывает баланс, уменьшает остаток товара и создаёт заказ в одной транзакции.

- `services.py` - реализация операции создания заказа.
- `setup.py` и `setup_stock.py` - подготовка исходных данных для двух сценариев.
- `race.py` и `race_stock.py` - стенды для проверки конкурентного выполнения.

В заданиях 1-4 изменяйте только `services.py`. В задании 5 дополнительно создайте Alembic-миграцию и отдельный проверочный скрипт.

Не изменяйте стенды, скрипты подготовки данных и их критерии проверки. Не отключайте конкуренцию и не подменяйте гарантию БД глобальным Python-локом на весь процесс. Сохраните интерфейс `create_order` и атомарность операции.

## Задание 0. Проверьте границу транзакции

Ориентировочное время: 3 минуты.

Запустите подготовку проекта:

```bash
python setup.py
```

Изучите `services.py`. Убедитесь, что списание баланса, уменьшение остатка и создание заказа входят в одну транзакцию. Найдите границу её фиксации и путь отката при исключении.

При откате изменения строк, выполненные в этой транзакции, не должны сохраняться частично. Далее проверьте, достаточно ли такой атомарности для корректной работы двух одновременных покупок.

## Задание 1. Диагностика гонки

```bash
python setup.py && python race.py
```

Стенд запускает `create_order` в двух потоках: пользователь `alice` совершает две покупки, хотя денег хватает только на один заказ. На исходной реализации стенд позволяет воспроизвести результат `ИТОГ: КРАСНЫЙ (N перерасходов)`, где `N` - значение счётчика нарушений. Если гонка не проявилась, повторите запуск.

Опишите последовательность действий двух транзакций:

- какие значения каждая транзакция читает из БД;
- в каком порядке происходят проверки, изменения и фиксация;
- почему обе проверки баланса могут пройти успешно;
- почему атомарность каждой отдельной транзакции не предотвращает наблюдаемое нарушение.

**Результат:** схема или последовательное описание выполнения двух транзакций, объясняющее результат стенда.

## Задание 2. Реализуйте первое решение

Измените `services.py` так, чтобы `race.py` показывал `ЗЕЛЁНЫЙ`: во всех 10 прогонах подряд должна успешно завершаться ровно одна покупка.

Вторая покупка должна завершаться предусмотренным отказом через исключение. Не маскируйте отказ успешным результатом; не оставляйте частичных изменений баланса, остатка или заказа.

Выберите способ защиты самостоятельно. Если нужна отправная точка для поиска, рассмотрите вопросы:

- Какое состояние данных должна учитывать вторая транзакция, чтобы корректно отказать в покупке?
- Как исключить решение на основе состояния, которое уже изменил конкурент?
- Можно ли связать проверку условия и изменение данных так, чтобы конкурент не нарушил корректность между ними?
- Какие возможности БД и SQLAlchemy обеспечивают выбранную гарантию?

**Критерий приёмки:** `race.py` проходит 10 прогонов подряд, а объяснение показывает, почему выбранный механизм устраняет гонку из задания 1.

## Задание 3. Реализуйте другое решение

Решите ту же задачу другим механизмом обеспечения корректности. Косметическое изменение кода или другой синтаксис того же механизма не считаются вторым решением.

Сохраните первый вариант, чтобы можно было сравнить обе реализации. Для второго варианта повторно выполните `race.py`.

Сравните решения:

- как каждое из них обрабатывает конкурентное изменение данных;
- что происходит со второй транзакцией при конфликте;
- где возможно ожидание, отказ или необходимость повторить операцию;
- какие ограничения и дополнительные затраты возникают;
- в каких ситуациях уместен каждый вариант.

Различие обоснуйте механизмом защиты. Полное отсутствие ожидания на уровне БД не является обязательным критерием второго решения.

**Критерий приёмки:** второй вариант также проходит 10 прогонов `race.py` подряд; объяснение показывает принципиальное различие двух решений и их компромиссы.

## Задание 4. Проверьте защиту остатка товара

Выберите одну из реализаций для дальнейшей работы и проверьте её на втором сценарии:

```bash
python setup_stock.py && python race_stock.py
```

Теперь два разных покупателя, `alice` и `bob`, одновременно пытаются купить последний товар: `stock = 1`.

- Если результат `КРАСНЫЙ`, объясните, почему защита баланса не обеспечила корректность остатка. Доработайте решение, чтобы `race_stock.py` стал зелёным, и повторно проверьте `race.py`.
- Если результат сразу `ЗЕЛЁНЫЙ`, объясните, какой механизм защищает общий остаток и как взаимодействуют транзакции разных покупателей. Одного успешного запуска для вывода недостаточно.

**Критерий приёмки:** итоговая реализация проходит по 10 прогонов подряд на каждом стенде. Вы можете объяснить, как она защищает и баланс пользователя, и остаток товара.

## Задание 5. Добавьте защиту на уровне схемы БД

Обеспечьте запрет на сохранение отрицательного баланса и отрицательного остатка товара, даже если прикладной код попытается записать такие значения без предварительной проверки.

- Самостоятельно выберите подходящие ограничения на уровне схемы.
- Оформите их Alembic-миграцией и примените её к учебной БД.
- Напишите отдельный короткий скрипт, который намеренно пытается нарушить каждое из выбранных ограничений, например списать больше, чем доступно, без проверки в коде.
- Покажите отказ БД и проверьте состояние данных после отката неуспешной операции.

В объяснении ответьте: предотвращает ли выбранное ограничение гонку из задания 1? Какое именно недопустимое состояние оно запрещает и зачем такая защита нужна вместе с решением из предыдущих заданий?

**Критерий приёмки:** миграция применяется, проверочный скрипт демонстрирует отказ БД при нарушении ограничений, а после отката данные сохраняют прежние значения. Гарантия ограничения и её границы объяснены.

## Правила проверки

- Каждый замер должен начинаться с исходного состояния данных. Для ручного запуска используйте соответствующий `setup.py` или `setup_stock.py`; стенды подготавливают данные перед каждым прогоном.
- Результат `ЗЕЛЁНЫЙ` засчитывается только после 10 последовательных прогонов без нарушения проверяемого условия.
- Сохраните вывод стендов для обеих реализаций из заданий 2 и 3, а также результаты обоих стендов для итоговой реализации из задания 4.
- Успешные прогоны дополняйте объяснением механизма: сами по себе они не заменяют обоснование корректности.
- Не изменяйте стенды и не подавляйте конкурентное выполнение средствами Python.
